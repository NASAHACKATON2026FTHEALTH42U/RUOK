# Architecture

## Stack
| Layer | Technology |
|---|---|
| Frontend | React 18 + Vite 6 + TypeScript 5.6 (strict), Tailwind 4 (`@tailwindcss/vite`), React Router 6, Zustand 5, Recharts 3, Framer Motion, IndexedDB (`idb`). ESLint 9 + Prettier. Versions and structure in [`frontend/README.md`](../../frontend/README.md) |
| Backend | Python 3.11+, FastAPI, SQLModel, SQLite (WAL mode), pytest |
| Contract | OpenAPI generated by FastAPI → TS types with `openapi-typescript` (`npm run gen:api`) → typed `openapi-fetch` client (`frontend/src/api/client.ts`) |
| Runtime | Local: two terminals (today). `docker compose up` will arrive with BE-24 (#39). FastAPI serves `frontend/dist` in "onboard" mode, listening on `0.0.0.0` so that **phones and tablets can connect over the local network** ([control-center-and-devices.md](control-center-and-devices.md)) |
| Real time | Server-Sent Events (`/events/stream`) + `event_log` table |

## Local-first principle
RUOK represents the **onboard computer**: all logic and knowledge live locally, and **nothing depends on the internet or on the connection with Earth**.
- The database, the assessment engine, the catalogs (indicators, protocols, interventions) and the gamification are all local.
- The link with Earth or with external control is **simulated** (`services/comm_link.py`) with a persistent queue that works as store-and-forward, in the style of delay-tolerant networks (DTN). See [alerts-and-escalation.md](alerts-and-escalation.md).
- The external control console (`/ground`) is also local: it is just another view of the same front end.
- **Multi-device:** each user can use their phone or tablet connected to the server over **local Wi-Fi without internet**. The **control center** (`/control`, admin) sees the whole data flow live and manages the application.
- **No HTTPS on the local network:** no APIs that require a secure context are used (`crypto.randomUUID`, service workers, camera). UUIDs are generated with `crypto.getRandomValues()`.
- No CDNs: fonts, icons and images are bundled.
- Offline and liveness details in [offline-and-liveness.md](offline-and-liveness.md).

## Key decisions
| Decision | Reason |
|---|---|
| Generic `members`, with each environment having its own members | Same model for astronaut, patient or resident; the visible text comes from `environment.vocabulary` |
| Optional `assessment?env=` | Re-assess the same data with another profile, to show it in the demo |
| Check-in and PVT stored as `measurements` | They reuse the charts, the assessment, offline mode and expiry without new tables |
| `/control` separate from `/ground` | `/ground` is the realistic medical view (with delay and privacy); `/control` is the operations view (everything, instantly) |
| SSE instead of WebSockets | Simpler, runs over plain HTTP, reconnects on its own and works in every mobile browser |
| IndexedDB per device (`ruok-<device_id>`) | Several devices or tabs on the same machine do not share a session or outbox |
| Injectable clock (`clock.py`) | Lets the demo speed up time (link ETA, liveness) |
| Front-end mocks shaped like the contract | The front end moves forward without waiting for the back end, and the demo survives if the back end goes down |
| *Append-only* measurements with a client UUID | Sync is idempotent and there are no conflicts |
