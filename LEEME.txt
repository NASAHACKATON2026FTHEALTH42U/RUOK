 1. REGLA DE ORO DE GIT (OBLIGATORIA)
------------------------------------------------------------------------------

  >>> NUNCA hagas push directo a main. <<<

  Desde el 15/11 el repo es público y GitHub BLOQUEA el push directo a main:
  todo entra por PR y solo se puede mergear con los 3 checks de la CI en verde.
  El force-push y el borrado de main también están bloqueados.

  Flujo:
    1. Coge una issue de tu área (ver sección 3) y asígnatela.
    2. git checkout main && git pull
    3. git checkout -b feat/<area>-<id>-<slug>
         ejemplos: feat/be-08-assessment-engine
                   feat/fe-05-body-figure
                   fix/sos-modal-offline
    4. Commits pequeños con el ID: "BE-08: umbrales por entorno"
    5. ANTES de abrir la PR, trae main a tu rama y pasa los tests:
         git fetch origin && git merge origin/main
         (resuelve conflictos en local; ver "Evitar conflictos" más abajo)
    6. git push -u origin <tu-rama>
    7. Abre una PR a main con "Closes #<n>" en la descripción.
    8. Espera a que la CI esté en VERDE (los 3 checks).
    9. 1 aprobación de alguien de tu área o del full-stack.
   10. JUSTO ANTES de mergear, si main ha avanzado: repite el paso 5.
   11. Merge con "Create a merge commit" (es lo que usamos) y BORRA la rama
       (botón "Delete branch" de la PR).

  NO se mergea:
    - con la CI en rojo o pendiente;
    - sin aprobación (excepción: P0 urgentes de madrugada con el visto bueno
      del supervisor; se avisa en el canal del equipo);
    - con force-push sobre main (prohibido siempre).

  EVITAR CONFLICTOS (ya nos han pasado: PRs #64, #88, #89 y #100, que dejó
  FE-09 fuera de main por estar apilada; se rescató en #104):
    - PRs PEQUEÑAS y mergeadas PRONTO. Una rama no debería vivir más de
      3-4 horas: cuanto más vive, más se aleja de main.
    - Sincroniza con main a menudo (git fetch origin && git merge origin/main),
      no solo al final. Siempre antes de abrir la PR y antes de mergear.
    - Una PR MERGEADA está cerrada: NO subas más commits a esa rama (se quedan
      fuera de main sin que nadie lo note). Lo siguiente va en una rama nueva
      desde main actualizado.
    - Si alguien sigue subiendo commits a una PR, avisa antes de mergearla.
    - NO apiles PRs (una rama encima de otra sin mergear). Si es inevitable:
      se mergea primero la de abajo y se avisa en la descripción.
    - Ficheros GENERADOS en conflicto (types.gen.ts, fixtures.gen.ts,
      package-lock.json, uv.lock): NO se resuelven a mano. Coge cualquiera de
      las dos versiones y regenera:
         cd frontend && npm run gen:api && npm run gen:mocks   (tipos y mocks)
         cd frontend && npm install                            (package-lock)
         cd backend  && uv lock                                (uv.lock)
    - Tras resolver un conflicto, pasa TODOS los tests (back y front) antes
      de hacer push.
    - Si resuelves un conflicto en la rama de OTRA persona, déjale un
      comentario en su PR explicando qué has tocado.

 2. CI (GITHUB ACTIONS) - .github/workflows/ci.yml
------------------------------------------------------------------------------

  Corre en cada PR y en cada push a main. Tiene 3 checks:

    Backend (pytest)                -> ruff check + pytest
    Frontend (lint + build)         -> npm run lint + npm run build + npm test
    Contrato API (tipos TS al día)  -> regenera types.gen.ts desde FastAPI
                                       y falla si no coincide con el repo

  Antes de abrir la PR, pasa lo mismo en local:

    BACK :  cd backend  && uv run pytest && uv run --with ruff ruff check .
    FRONT:  cd frontend && npm run lint && npm run build && npm test

  Si la CI falla, lo arreglas tú en tu rama. No se mergea "y luego lo arreglo".

------------------------------------------------------------------------------
 4. CONTRATO DE LA API (FRONT <-> BACK)
------------------------------------------------------------------------------

  Fuente de verdad: docs/api-contract.md

  Si cambias la API (BACK):
    1. Actualiza primero docs/api-contract.md (en la misma PR).
    2. Cambia backend/app/schemas/ (un módulo por dominio) y los routers.
    3. Regenera tipos y mocks del front: cd frontend && npm run gen:api && npm run gen:mocks
    4. Commitea types.gen.ts y fixtures.gen.ts. Si no, "Contrato API" o el build fallan.
    5. Avisa al equipo FRONT en el canal.

  FRONT:
    - Nunca edites src/api/types.gen.ts a mano.
    - Toda llamada pasa por src/api/client.ts y toda escritura por el outbox
      (src/offline/outbox.ts).
    - Mientras el back no esté listo, usa los mocks (VITE_USE_MOCKS=true).

 5. PRINCIPIOS DEL PRODUCTO (NO NEGOCIABLES)
------------------------------------------------------------------------------

  1. Sin datos = DESCONOCIDO. unknown / stale / lost NUNCA se pintan en verde.
  2. Local-first. Nada de nube, CDNs ni internet en tiempo de ejecución.
  3. Sin pérdida de datos. Todo POST lleva un UUID del cliente y es idempotente.
  4. Configuración, no código. Umbrales, entornos y protocolos van en
     backend/app/data/*.json.
  5. Reloj de demo: en el back usa app/clock.py (now()), nunca datetime.now().
  6. Texto visible desde environment.vocabulary: nunca "astronauta" fijo.
  7. Privacidad conductual: detalles de ánimo ocultos salvo que el member los
     comparta o haya una emergencia.
  8. Login y roles (docs/auth-and-roles.md): el BACKEND valida rol y propiedad
     en cada endpoint; ocultar en el front no es seguridad. El SOS funciona
     SIN sesión y un 401 nunca borra el outbox.
  9. Multi-dispositivo en red local (docs/control-center-and-devices.md):
     los móviles entran por http://<IP>:8000 SIN HTTPS -> no uses
     crypto.randomUUID() ni service workers. Vistas de member mobile-first.
     Todo cambio de estado en el back emite un evento (events.emit) para el SSE.
 10. Disclaimer: NO es un dispositivo médico.
